# Ключи доступа администратора

## Что включается

Администратор сначала входит в существующий аккаунт, затем подтверждает доступ отдельным FIDO2 USB/NFC-ключом с PIN или биометрией. После личной регистрации первого ключа проверка становится обязательной для этого аккаунта: в интерфейсе, HTTP/callable API, Firestore и Storage.

До первой регистрации политика **не включена**. Публикация кода сама по себе не означает, что физический ключ уже зарегистрирован. Первая регистрация доверяет текущему администратору с входом не старше пяти минут; выполнять её следует лично на доверенном устройстве. Это не резервный способ обойти уже включённую защиту.

## Первое включение

1. Подготовьте совместимый FIDO2-ключ и желательно второй резервный.
2. Откройте [Zmena](https://tren-85720.web.app/) в обычном Chrome, Edge или Safari. Ключ привязан к `tren-85720.web.app`, не к localhost или другому домену.
3. Войдите в свой существующий аккаунт администратора заново.
4. Откройте «Настройки и выход» → «USB/NFC-ключи доступа».
5. Нажмите «Добавить ключ и включить», выберите отдельный ключ, выполните запрос браузера: PIN/биометрия и касание.
6. Убедитесь, что появился статус «Вход защищён ключом». Затем добавьте резервный ключ и храните его отдельно.
7. После выхода проверьте новый вход основным и резервным ключом. Пароль сам по себе больше не открывает админские данные.

При отмене браузерного запроса доступ не подтверждается. Встроенный браузер Telegram может не поддерживать ключи: используйте обычный браузер. Облачные синхронизируемые passkeys не принимаются. Без attestation/доверенного списка производителей система проверяет single-device WebAuthn, а не сертификацию модели аппаратного устройства.

## Сессия и защита данных

- Подтверждение действует не более восьми часов, затем требуется ключ снова. Новый вход без этого подтверждения заблокирован.
- Proof находится в подписанном токене конкретного входа; он не записывается в глобальные `customClaims`, localStorage или настройки клиента.
- Proof привязан к версии ключевой политики и текущей выдаче роли администратора. Отзыв/перевыдача роли не сохраняет прежнее подтверждение.
- Challenges одноразовые, действуют пять минут, привязаны к UID, входу, версии роли, действию и политике. Origin/RP, подпись, user verification, counter и гонки проверяются сервером.
- Credential public keys и challenges доступны только Admin SDK. Поля политики нельзя менять обычным SDK, в том числе из админского интерфейса.
- Можно добавить до пяти ключей. Удаление всех ключей и парольный обход в приложении не предусмотрены.

## Потеря всех ключей

Сброс пароля не отключает ключ. Восстановление выполняет владелец Firebase-проекта вне приложения после отдельной проверки личности администратора. Не передавайте пароли, токены или секреты в чат.

Порядок для доверенного оператора: проверить личность → отозвать refresh tokens → заблокировать/перевыдать текущую админскую роль с новой `adminClaimVersion` → из доверенного Admin SDK удалить утраченные credentials/challenges этого UID и сбросить его ключевую политику → лично повторить первичную регистрацию и добавить резервный ключ. Не удалять аккаунт или пользовательскую историю. Универсального публичного recovery API нет.

## Проверка выпуска

Локальные проверки включают настоящую криптографическую верификацию WebAuthn, replay/origin/RP/UV/role/session/counter/race негативные сценарии, Rules emulator и изолированный браузерный UI. Они не заменяют личную проверку настоящим ключом после регистрации.

Изменённые Security Rules — проверенный тестами прототип защиты: они ограничивают административный доступ подписанным proof и запрещают клиентское изменение политики. Перед широким запуском их следует дополнительно проверить независимым ревью. Полной гарантии отсутствия уязвимостей нет.

Автоматическое TTL-удаление challenge-документов не включалось: срок верификации всё равно ограничен сервером. Настройка фонового удаления и аппаратная attestation могут быть отдельным этапом, без изменения пользовательской истории.
