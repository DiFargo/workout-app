# Глубокий аудит архитектуры загрузки Zmena

Дата: 25 октября 2026 года. Проверенная база: **3.0.869**. Стадия продукта: закрытое тестирование, ориентир — до 100 клиентов.

## Главный вывод

Проблема не сводится к «слишком много данных одновременно». В приложении пересекаются четыре разных вида работы: загрузка кода, получение данных экрана, проверка актуального доступа и отправка локальных изменений. Сейчас у части ресурсов несколько инициаторов; часть истории нужна для принятия решений, а не только для отображения. Простая очередь или добавление `limit(20)` могут уменьшить трафик, но создать неверный прогресс, потерю изменений или запуск старого назначения.

Рекомендуемое направление: **единое управление запросами и ревизиями → приоритеты экранов → компактные производные данные → безопасная загрузка истории по частям**. Сохранять существующую архитектуру React + Firebase и внедрять небольшими независимыми выпусками. Переписывание `AppCore`, переход на другой фреймворк или новую инфраструктуру для этого не нужны.

Код приложения, версия, правила доступа и Production в рамках этого анализа **не изменялись**. Созданы только локальные диагностические материалы и этот отчёт.

## 2. Как приложение загружается сейчас

Упрощённый граф фактических зависимостей:

```text
main → CSS + блокировка второго экземпляра Telegram → import(App) → React
  → Auth-сессия → профиль + проверка claims → роль и актуальный доступ
    → план тренировок: workouts + профиль + ПОЛНАЯ история
    → одновременно фон: история + питание + замеры + фото-метаданные + задачи
      → после завершения всей этой фоновой группы: повтор offline-очередей

finishAuth → собственное чтение профиля → ещё история + план
открытие «Тренировки» → ещё проверка плана
```

Оболочка уже не ждёт всю фоновую группу, а медиа не обязаны блокировать готовность плана. Однако «не await в оболочке» не означает «не конкурирует за сеть/CPU». Кроме того, очередь несохранённых изменений ждёт завершения разнородных фоновых чтений.

Основные точки:

- [Стартовые загрузки и offline-повторы](C:/Users/workk/workout-app/src/app/appBootstrapHelpers.js:388).
- [Второй инициатор в finishAuth](C:/Users/workk/workout-app/src/features/auth/authHandlers.js:174).
- [Три чтения, необходимые нынешнему загрузчику плана](C:/Users/workk/workout-app/src/features/client/workouts/workoutFirebaseLoadHandlers.js:142).
- [Повторный вход во вкладку тренировок](C:/Users/workk/workout-app/src/features/client/workouts/workoutEntryNavigation.js:76).

### Что уже сделано правильно

Существуют ленивые маршруты, привязка асинхронных ответов к Auth-сессии, ограничения сводок тренера и признаки неполноты. Каталог питания прогревается при открытии поиска, а не целиком при старте. Фото-метаданные не равны загрузке всех изображений. Предзагрузка обложек уже ограничена ближайшими упражнениями и памятью; MP4 не нужно скачивать до Play. Эти механизмы следует сохранить, а не создавать параллельную систему поверх них.

Глобальная подписка на профиль нужна в том числе для отзыва доступа. Её удаление ради сокращения одного слушателя — неверная оптимизация. Аналогично нельзя заменить проверенную роль значением из старого локального профиля.

## 3. Подтверждённые проблемы и их приоритет

Приоритеты ниже обозначают порядок исправлений, а не подтверждённые инциденты у реальных пользователей.

### P1. У ресурса несколько инициаторов, нет общего объединения одинаковых запросов

Локальный прогон настоящих обработчиков в ограниченном контуре Auth/план/история дал:

| Сценарий | Логические чтения Firestore | Вызовы API |
| --- | ---: | ---: |
| Bootstrap без отдельного finishAuth | 6 | 1 |
| finishAuth вместе с bootstrap | 11 | 3 |
| Повторный вход в раздел тренировок | 3 | 1 |

Вторая строка включает дополнительную запись профиля, третья — запись предпочитаемого режима. Внутренние запросы питания, замеров, фото и задач в эти числа **не включены**. Это не полный React-прогон, не число документов и не расчёт стоимости: Firebase может использовать кэш и собственное объединение сетевых операций.

Нужен один владелец получения ресурса, а не запрет вызова из других мест: все инициаторы запрашивают один контракт и получают общий незавершённый Promise по одинаковому ключу. Явное обновление и смена назначения создают новую ревизию, а не случайно используют старый Promise.

### P1. Более старый ответ истории может заменить новый

Проверка [loadHistory](C:/Users/workk/workout-app/src/features/client/workouts/workoutHistoryHandlers.js:59) воспроизвела два запроса одной сессии: второй завершился первым, затем первый перезаписал его результат. Защита от другой Auth-сессии есть, но она не решает гонку внутри той же сессии.

Добавить поколение запроса и версию ресурса; перед применением ответа проверять их вместе с сессией. Для локально изменяемых данных сравнивать ещё и ревизию мутаций: просто «последний запрос победил» не должен затереть изменения, сделанные во время чтения.

### P1. «План готов» не отделяет серверный ответ от кэшированного

В локальном адаптере одинаковый план с `metadata.fromCache=false` и `true` получает подтверждение и состояние `ready`. [Механизм подтверждения](C:/Users/workk/workout-app/src/features/client/workouts/workoutFirebaseLoadHandlers.js:297) учитывает сессию/режим/ссылку плана, но не происхождение snapshot.

Это **не доказательство обхода Firestore Rules или реальной работы приложения offline**. Это обнаруженное свойство загрузчика. Необходимо раздельно хранить «есть что показать», «получено с сервера», «разрешено начать» и «есть неподтверждённые изменения». В Firebase `fromCache` специально обозначает потенциально устаревший/неполный результат. [Документация Firebase](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

Дополнительно [ветка перезапуска без черновика](C:/Users/workk/workout-app/src/features/client/workouts/workoutOpenHandlers.js:341) в синтетическом сценарии открывает `fallbackPlan` старого назначения, если свежий ответ больше не содержит эту тренировку. Следует показывать изменение назначения и переходить к актуальному плану, не подставлять старый объект в разрешённое действие. Это также проблема устаревшего UI, а не доказанный обход серверного доступа.

### P1. Питание может сохраняться обратно после чтения без пользовательских изменений

Исполнены реальные loader, React effects, merge/save, localStorage и offline-очередь; только Firebase I/O заменён локальным адаптером. На уже каноническом состоянии с `updatedAt`, без правок пользователя:

1. Гидратация делает два `getDoc`, затем autosave — одну транзакцию с двумя `set`.
2. Минутное обновление повторяет это: ещё одна транзакция с двумя `set`.
3. Семантический hash облачного состояния до и после обеих записей одинаков.

При отрицательном контроле без `updatedAt` транзакций нет. Первая запись для legacy-нормализации или накопленных offline-правок может быть нужна; нельзя просто «пропустить первый effect».

Причина: [гидратация создаёт новый объект](C:/Users/workk/workout-app/src/features/client/nutrition/nutritionCloudLoader.js:59), а [autosave](C:/Users/workk/workout-app/src/features/client/nutrition/useNutritionRuntimeEffects.js:135) не различает чтение и локальную правку. Минутный refresh действует независимо от активного раздела. Нужны отдельные `cloudRevision`, `dirtyRevision`, `ackedMutationRevision`.

На 7 синтетических днях гидратация с autosave передала в `localStorage.setItem` суммарно 85 875 байт JSON-значений, следующий refresh — ещё 122 427. Это сумма аргументов API с повторениями и backup, **не физическая запись диска и не размер данных реального клиента**. Оптимизировать происхождение изменений полезнее, чем только увеличивать интервал.

### P2. Полная история тренировок находится на пути открытия плана

Нынешний загрузчик использует историю для определения выполненных тренировок активного назначения. Поэтому загрузка ограниченной страницы вместо полной истории без изменения контракта может повторно предложить выполненную тренировку.

Синтетическая история из 1 000 записей: полный JSON — 6 351 781 байт; проекция идентичности/выполнения — 367 781 байт. Desktop `stringify` полного набора — около 16,3 мс; расчёт временной шкалы — около 0,54 мс. Основной доказанный риск здесь — растущий объём чтения и зависимость старта от него, **не установленная причина секундных задержек CPU на телефоне**.

Нужен компактный индекс выполнения текущего назначения; полная история остаётся отдельной страницей. Но этого индекса недостаточно: из всей истории сейчас также вычисляются предыдущие веса и подходы упражнений. Для них нужен отдельный контракт последних результатов, описанный ниже. Перед внедрением согласовать семантику сочетания «тренер отметил пропуск» и «пришла запись о выполнении»: в текущих представлениях воспроизведено расхождение. Индекс не должен закрепить эту неоднозначность.

### P2. Питание хранится монолитом, поэтому ступенчатая загрузка пока лишь переносит тот же объём

Текущее чтение `nutrition/state` возвращает все дни. Добавление клиентского фильтра по дате не уменьшит чтение этого документа.

| Синтетические дни, по 6 продуктов/день | JSON состояния | Медиана merge на desktop |
| --- | ---: | ---: |
| 7 | 12 063 байт | 0,04 мс |
| 90 | 152 232 байт | 0,44 мс |
| 365 | 618 297 байт | 1,86 мс |

365 дней уже превышают внутренний предупредительный порог 614 400 байт, но ниже ограничителя сохранения 768 000. Это UTF-8 JSON, не точный размер документа Firestore; набор не моделирует большую личную базу продуктов. Один последний день — около 1,7 КБ. Потенциал разделения существенен, но требует миграции writer, а не только loader.

### P2. Кабинет тренера размножает чтения по числу клиентов

Для глубокой сводки каждого клиента сейчас до шести источников. При холодном успешном прогоне модель даёт `6 × N` логических чтений только на сводки. Для администратора со списком и библиотекой: `1 + 6N + 2` — **123 операции для 20 строк, 603 для 100**. N — строки, переданные в сводки, а не подтверждённое число настоящих клиентов; это модель исходников, не Production-замер.

У загрузчика есть четыре работника, но внутри каждого шесть источников: до 24 обёрнутых обещаний одновременно, плюс операции вне этой группы. Таймаут обёртки не отменяет уже запущенный Firebase I/O. Поэтому ограничение «4 клиента» не является глобальным сетевым лимитом.

TTL 60 секунд полезен, но ключ сводки не содержит ревизии каждого источника истории/питания/замеров. На большом списке нужна маленькая готовая сводка и первая страница клиентов, а не чтение шести коллекций для всех строк. Карточка клиента также содержит последовательные чтения и финальную загрузку библиотеки; её вкладки должны иметь независимую готовность.

### P2. Маленький entry не означает маленькую фактическую загрузку приложения

`App` импортируется сразу после entry. Его статические зависимости содержат не только текущий экран. Крупнейшие gzip-части обязательного замыкания: `App` около 174 КиБ, Firebase 159 КиБ, React 66 КиБ, CSS `App` 29 КиБ. Часть тренерских вычислений/утилит присутствует до открытия тренерского маршрута.

Дополнительные ленивые маршруты сверх boot: список тренировок около 48 КиБ, тренировка 74 КиБ, питание 89 КиБ; тренерские маршруты около 318–330 КиБ каждый по статическому замыканию. Они имеют общие зависимости, поэтому складывать их как три независимых скачивания нельзя.

Нужны границы владения зависимостями и измерение **полного пути до полезного экрана**, а не только размера `index`. Существующие lazy routes сохраняются. Сам по себе `React.lazy` откладывает компонент до первого рендера; немедленный рендер или прямой импорт общих зависимостей не даёт ожидать экономии до позднего действия. [Документация React](https://react.dev/reference/react/lazy).

## 4. Целевая архитектура: не одна очередь, а три независимых контура

```text
Проверка сессии / роли / назначения ──→ разрешение действий и инвалидирование кэша
                  │
                  ├─→ данные видимого экрана ──→ локальная готовность раздела
                  │           └─→ ограниченная предзагрузка ближайшего действия
                  │
Локальная правка → надёжная очередь → подтверждение сервера → обновление ревизий
```

### Контур A. Актуальный доступ и управление

Оставить быструю, независимо работающую проверку Auth-сессии, роли, назначения и отзывов доступа. Профиль, уже полученный bootstrap, можно повторно использовать только с известной ревизией/достоверностью, не превращая старый локальный профиль в доказательство доступа. Проверка администратора и подписка на актуальный профиль не должны ждать загрузки питания или библиотеки.

### Контур B. Чтения для экрана и фоновая работа

Добавить небольшой общий слой ресурсов рядом с существующими loader, без переноса всей логики в один компонент. Обязательные возможности:

- Объединение одинаковых незавершённых запросов (`single-flight`).
- Ключ: сессия/её поколение, целевой UID, контекст роли и назначения, тип ресурса, диапазон/курсор, версия схемы. UID недостаточно при повторном входе или переназначении.
- Поколение запроса и ревизия результата; старый ответ не применяется поверх нового.
- Раздельная готовность разделов и явная полнота данных.
- Приоритет видимого экрана; низкоприоритетные задания ещё **не запускать**, если появились более важные.
- При уходе с экрана отменять поддерживаемый `fetch`, а для неотменяемых чтений не применять ответ после смены владельца. Не выдавать таймаут за отмену.

Начальный ориентир для эксперимента: 1–2 фоновых задания, отдельная ёмкость для доступа/видимого экрана, медиапредзагрузка с собственным малым лимитом. Это **не готовая константа для Production**: единица — источник/задание, а не клиент с шестью вложенными запросами. Независимые чтения, которые нужны одному экрану сейчас, оставлять параллельными; общая последовательная очередь создаст новую «водопадную» задержку.

Необязательно сразу устанавливать SWR/TanStack Query. Сначала нужен описанный контракт и проверка существующих guards/outbox. Выбор готовой библиотеки оправдан, если она уменьшит собственную сложность без второго кэша и без потери семантики назначения.

### Контур C. Надёжная запись и восстановление

Очередь пользовательских изменений не является обычной предзагрузкой. Она должна переживать закрытие приложения, повторять операции идемпотентно и подтверждать только отправленные ревизии. Нельзя откладывать её за загрузку всех фото/замеров, но нельзя и отправлять старый полный snapshot поверх нового облачного состояния без merge.

Последовательность: восстановить pending → проверить текущую сессию/схему/назначение → получить нужный конкретной операции baseline → согласовать и отправить → удалить только подтверждённые операции. Другие фоновые данные не являются обязательным барьером.

## 5. Состояние кэша должно иметь несколько независимых измерений

| Измерение | Примеры | Почему не хватает `loaded=true` |
| --- | --- | --- |
| Доступ | неизвестен / подтверждён / отозван | Данные в памяти не разрешают действие |
| Доступность | нет / загружается / есть / ошибка | Ошибка обновления не равна пустому ресурсу |
| Полнота | конкретный день / диапазон / страница / всё назначение | Первая страница не доказывает отсутствие старой записи |
| Свежесть | кэш / обновляется / подтверждено сервером, revision | Старое можно показать, но не всегда использовать для старта |
| Синхронизация | чисто / pending / отправляется / конфликт | Свежий cloud snapshot не должен удалить локальную правку |

Для UI нужны понятные состояния «обновляем», «нет связи», «изменения ещё не отправлены», а не бесконечный общий экран загрузки. Незагруженный день питания — не нулевые калории; неполная история — не «тренировок не было».

Кэш данных и надёжная очередь — разные хранилища. Для больших snapshots/очередей можно отдельно оценить IndexedDB, но только с проверяемым переносом и сохранением исходной копии до подтверждения. Нельзя обрезать tombstones, очередь и пользовательскую историю ради скорости.

Включение постоянного Firestore-кэша само по себе не решает эту модель: в Web он не включён по умолчанию, а сохранённые данные требуют политики доверенного устройства/очистки. Это отдельное решение, не незаметная оптимизация. [Документация Firebase](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

## 6. Контракты загрузки по экранам

| Экран | Для первой полезной отрисовки | После готовности / по действию |
| --- | --- | --- |
| Вход | Лёгкий auth UI и нужный способ входа | Код авторизованных разделов после успешной сессии |
| «Сегодня» | Проверенная роль, компактный профиль/назначение, текущие задачи и сводки | Детальная история, фото, библиотека — по открытию |
| «Тренировки» | Актуальное назначение, план, компактное выполнение этого назначения, черновик | История страницами; обложки ближайших упражнений |
| Открытое упражнение | Текущий подход, предыдущие результаты по совместимому контракту, доступная обложка, таймер, локальные изменения | Видео только по Play; следующая обложка с ограничением |
| Питание | Выбранный день, цели, состояние pending | Соседний день/диапазон по намерению; личная база/каталог при поиске |
| Прогресс / мастер замеров | Последний вес отдельно от последнего полного/body-замера | График за выбранный период, фото-метаданные страницами, изображение по видимости |
| Список тренера / администратора | Первая страница разрешённых строк и компактные сводки | Следующая страница, поиск, детали выбранного клиента |
| Карточка клиента | Профиль и сводка; доступ проверяется независимо | История, питание, фото, платежи и заметки — отдельные вкладки |
| Редактор программы | Полный выбранный редактируемый документ и его revision | Библиотека упражнений отдельно, с поиском/страницами |

Редактору нельзя передавать частичную программу как полную и затем сохранять её нынешним full-document writer: это удалит невидимые элементы. Экспорт — отдельный проход по всей истории, не экспорт видимой первой страницы.

## 7. Какие компактные данные нужны вместо полных коллекций

### Выполнение текущего назначения

Производный документ/набор должен быть связан с версией назначения и идентичностью конкретного прохождения, а не только с названием упражнения или ID шаблона. Минимум: версия схемы, assignment ID/version, ревизия источников, выполненные вхождения с происхождением доказательства, текущий следующий элемент, признак полноты backfill. Сохранённый результат, ручной статус `completed` и календарная отметка — самостоятельные основания; их нельзя схлопнуть в один необъяснимый boolean.

Индекс обновляется при сохранении, удалении/исправлении истории, ручного статуса, календаря и смене назначения. Удаление записи истории снимает её основание, но не обязано отменять независимый ручной `completed`. Повторный `clientSaveId` не удваивает выполнение; tombstone предотвращает возврат удалённого результата. Нынешние проверки prescription/assignment в транзакции сохранения сохраняются: результат старой тренировки может попасть в историю, но не должен продвинуть новую программу.

До готовности backfill — безопасная совместимая ветка с нынешним полным чтением, а не ложный пустой индекс. После готовности можно пагинировать визуальную историю курсорами со стабильной сортировкой и дополнительным ID при равных датах. Firebase рекомендует курсоры, а не offsets. [Практики Firestore](https://firebase.google.com/docs/firestore/best-practices?hl=en).

### Предыдущие результаты упражнений

[buildWorkoutPageDerivedState](C:/Users/workk/workout-app/src/utils/workoutPageDerivedState.js:28) выбирает последние результаты из всей истории с фильтром версии назначения, ключом ID упражнения и legacy-fallback по нормализованному имени. Пагинация общей истории может убрать нужный результат за пределы первой страницы. Нужен отдельный `LatestExerciseResults` для текущего контекста назначения либо совместимое полное чтение до готовности этого ресурса.

Сохранять источник результата, дату, ревизию назначения и исходные подходы, а не только готовую строку. Удаление/исправление последней записи требует поиска предыдущей или rebuild; повторное назначение шаблона не подхватывает чужое прохождение. Сначала воспроизвести текущую семантику, не расширять автоматически сравнение на все старые программы. Этот контракт и индекс выполнения должны пройти сверку **до** ограничения общей истории.

### Последний вес и последний body-замер

Нужны **два независимых указателя/снимка**. Быстрый `weight_checkin` во вторник не должен вытеснять объёмы понедельника в полном мастере. При этом body-запись может быть частично заполнена: нельзя выдумывать отсутствующие из 12 полей или смешивать разные даты в один «последний замер».

Хранить источник, нормализованную дату и revision. Удаление/исправление последней записи инвалидирует снимок; запоздавший старый offline-замер не откатывает новый. Для legacy дат `date/createdAt/savedAt` нужен backfill, а не слепое `orderBy(date).limit(1)`. Сохранить нынешнюю семантику графика: семь последних записей, затем фильтр веса; переход на «семь последних валидных весов» — отдельное продуктовое изменение.

### Сводка для тренера

Серверная производная сводка по клиенту: необходимые числа/даты/статусы, ревизии источников, `generatedAt`, признаки `complete/limited/stale`. Без приватных заметок другого тренера, подписанных URL или сырых фото. Это ускоритель отображения, **не источник разрешения доступа**.

Предпочтительнее повторяемый пересчёт по ревизии с объединением близких событий, чем слепые `+1/-1`: события и повторные запросы могут приходить не по порядку. Поздний пересчёт не заменяет более новый. Старое назначение тренера инвалидируется при переназначении; новый тренер получает только разрешённый ему контекст.

| Событие | Что инвалидировать/пересчитать |
| --- | --- |
| Сохранение, удаление, исправление тренировки | Выполнение назначения, история, сводка тренера |
| Изменение дня питания | Этот день, нужные диапазоны/итоги, сводка питания |
| Новый/удалённый/исправленный замер | Соответствующий latest-снимок, график, сводка |
| Смена программы/календаря | Кэш назначения, следующий workout, право продолжения черновика |
| Смена тренера/роли/доступа | Сначала доступ и scoped-кэш, затем разрешённые сводки |
| Новая задача/платёж/переход календарного дня | Соответствующие статусы и времязависимые итоги |

## 8. Питание: безопасная миграция, без двух источников истины

Первый выпуск — только устранение echo-save и разделение dirty/ack, без смены схемы. Затем целевая схема: небольшой manifest/config и документы конкретных дней в активном поколении. Личная база продуктов мигрируется независимо. Названия, порции и макросы в истории сохраняются как снимки; изменение карточки продукта не переписывает старую еду.

Предлагаемый manifest содержит `sourceOfTruth`, `generation`, `writerEpoch`, состояние миграции и проверенную ревизию legacy. Конкретный день имеет `dayKey`, revision, записи, field/entity revisions и tombstones. Дата — календарный день пользователя с явной политикой timezone, не автоматически UTC.

Переход:

1. Legacy остаётся авторитетным; делается теневой backfill без изменения исходных данных.
2. По каждому дню сверяются порции, вода, макросы, IDs и удаления; проверяются новые изменения и offline-очереди.
3. Решается совместимость старых клиентов: единый совместимый server writer либо серверный запрет старого writer с понятным upgrade. Одного frontend-флага недостаточно.
4. После проверки атомарно переключаются активное поколение и writer epoch.
5. Новый writer подтверждает `mutationId` и committed revision; повтор не дублирует порцию. Частично загруженная карта дней никогда не передаётся старому full-state saver.

Независимый клиентский dual-write в legacy и days не рекомендуется: частичный сбой создаёт два разных состояния. Legacy offline snapshot также нельзя слепо превратить в «пользователь изменил все дни»: требуется сверка с baseline и сохранение исходной очереди до ack производных операций.

Rollback после новых дневных записей — не переключение на устаревший монолит. Сначала нужна актуальная проверенная проекция. Если полная история больше не помещается в legacy budget, нужен совместимый новый reader/roll-forward, а не обрезание истории. Никакого восстановления старого кода или старого backup поверх свежих дней.

## 9. Превью и видео: отдельный путь с защитой доступа

Текущая предзагрузка 3.0.869 уже дала улучшение по подтверждению пользователя. Дальше не следует прогревать все ролики или все обложки библиотеки.

До картинки у защищённого медиа существует управляющая цепочка: App Check → Auth/профиль/политика → лимит → метаданные/подпись → получение WebP. Предзагрузка скрывает ожидание, но не уменьшает количество этих операций. Для K отдельных холодных обложек часть проверок повторяется K раз; общий per-UID документ лимита также может стать точкой конкуренции. Реальная доля задержек этого пути в данном аудите не измерялась.

После инструментирования сравнить:

- Запрос только poster до Play; подпись видео — при запуске, без ухудшения его задержки.
- Малый пакет, например до трёх разрешённых poster: общие Auth/профиль/лимит, но проверка доступа и метаданных для каждого элемента. Лимит считать по элементам, а не «один пакет = одна картинка».
- Объединение одновременных запросов одного poster и сохранение существующего ограниченного memory cache.

Отдельный облегчённый сервис оправдан только после доказанной задержки cold start. Перенос helper в другой файл сам по себе не отделяет тяжёлые импорты функции. Постоянные оплачиваемые экземпляры пока не предлагаются. Нельзя делать обложки публичными, складывать signed URL в постоянную сводку или сохранять приватные ответы общим service worker.

## 10. Продуктовые решения, которые нельзя скрыто принять при оптимизации

1. **Старт без сети и немедленный отзыв доступа.** Гарантировать одновременно автономный старт и знание о только что отозванном доступе без связи невозможно. Рекомендуемый исходный вариант: локальное отображение/сохранение черновика с явным статусом; новые действия по назначению — по отдельно согласованной политике проверки. Не менять нынешнее поведение незаметно.
2. **Пропуск против offline-выполнения.** Нужны идентичность вхождения и порядок ревизий, чтобы не считать любое позднее событие безусловно главным. Это особенно важно перед новым completion index.
3. **Допустимая устарелость сводок.** Например, до минуты для обзорных чисел может быть приемлемо, но действия назначения/удаления/доступа требуют актуальной проверки. TTL статистики не применяется ко всем ресурсам одинаково.
4. **Два устройства меняют одну запись.** Сначала сохранить нынешнюю семантику merge. Более строгий UX разрешения конфликта вводить отдельно; оптимизация хранения не должна молча сменить победителя конфликта.

Эти решения не мешают первому этапу устранения дублей и echo-save. Они нужны перед изменением полномочий offline-режима и источников истины.

## 11. Рекомендуемый порядок внедрения и приёмка

Не публиковать всё одним большим изменением: после каждого этапа должен оставаться рабочий независимый результат.

| Этап | Изменения | Обязательная приёмка | Возможность отката |
| --- | --- | --- | --- |
| 1. Достоверность и наблюдаемость | Счётчики фаз без содержимого данных; single-flight; generation guards; dirty/ack; убрать старый fallback из разрешённых действий | Ноль сохранений при неизменном чтении; offline pending сохраняются; старый ответ не побеждает новый; смена сессии/назначения безопасна | Новые адаптеры отключаемы; схема данных прежняя |
| 2. Приоритеты без миграции | Отдельная готовность экранов; отложить ненужные замеры/фото/задачи; outbox без общего фонового барьера; bounded prefetch | «Тренировки» не ждут питание/фото; независимые нужные чтения параллельны; запись и отзыв доступа не голодают | Возврат прежнего планирования без потери очереди |
| 3. Границы кода и медиа | Точечные import boundaries; измерение poster-only/малого пакета | Меньше полный boot-объём, а не только entry; нет поздней поломки маршрутов; приватность и Play сохранены | Изолированные пути с совместимым API |
| 4. Компактные производные данные | Completion index с происхождением отметок, последние результаты упражнений, latest-замеры, сводка тренера; теневой backfill/сверка | Совпадение с историей и предыдущими весами/подходами; delete/replay/reassign; неполнота известна; серверный доступ не зависит от summary | Сохраняется проверенная legacy-ветка чтения |
| 5. История и кабинеты по частям | Cursor pagination, первая страница клиентов, независимые вкладки | Нет пропущенных/дублированных строк; экспорт полный; лимиты не искажают прогресс; editor не сохраняет partial | Старые источники сохранены на период проверки |
| 6. Дневные документы питания | Поколения, writer epoch, совместимость очередей, cutover | Сверка каждого дня; старые writers закрыты/совместимы; повтор/удаление/конфликт безопасны; проверены Rules и индексы | Только после актуальной проекции; иначе roll-forward |

Для первого результата разумно ограничиться этапами 1–2. Они убирают доказанную лишнюю работу без рискованной миграции. Этапы 4–6 дают устойчивость к росту истории и числа клиентов, но требуют отдельной проверки данных.

### Какие измерения добавить при реализации

Отмечать монотонное время фаз: оболочка, Auth, роль/назначение, полезные данные экрана, готовность старта, poster decode, Play→первый кадр, pending→ack. Для каждого задания — тип, причина, длительность, источник cache/server, объём/число записей, повтор/объединение, устаревший ответ. Не собирать email, UID в открытых отчётах, названия личных записей, содержимое питания/заметок или signed URL.

Сравнивать до/после на одинаковых синтетических аккаунтах и настоящем Telegram Android/iOS: холодный/тёплый запуск, медленная связь, отсутствие сети, возврат после закрытия, повторный вход того же UID, смена тренера во время чтения, два устройства. Отдельные наборы: 7/90/365 дней питания; 0/100/1 000 тренировок; 20/100 клиентов.

Предварительные цели для согласования, а не обещания: повторный показ уже готового раздела без полного блокирующего экрана; ноль MP4 до Play; одна незавершённая загрузка на ключ ресурса; ноль echo-save без dirty; ограниченный фоновый объём, не растущий со всей историей. Для будущих runtime-выпусков нужны профильные тесты изменённого контура, build и smoke соответствующих ролей/сценариев. Повторять все 1 700+ проверок после каждого документа или изолированного измерения не нужно. Текущий аудит не требует новой runtime-версии.

### Что пока не завершено

`clientLoadingSnapshot` сокращает передачу данных на телефон, но пока читает полные исходные коллекции на сервере. Это **не** материализованный индекс и **не** доказанное снижение оплачиваемых чтений Firestore. Постоянные индексы выполнения, последних результатов, замеров и тренерских сводок требуют отдельного теневого сравнения, backfill и согласованной инвалидации во всех путях записи/удаления/переназначения.

Полная клиентская история пока загружается по требованию раздела, но ещё не переведена на отдельную курсорную визуальную ленту. Каталог пользователей администратора пока читается целиком; карточка тренера всё ещё объединяет несколько источников общим ожиданием. Догрузка для экспорта и раздельные вкладки остаются отдельными критериями следующего этапа. Нельзя исправлять это простым `limit()` в общем массиве: он используется для итогов, AI и предыдущих результатов.

В кабинете клиента потребность пока определяется разделом, а не отдельной вкладкой: открытие настроек также может запустить полную историю, замеры и питание. Фотографии и задачи на главной загружаются фоном, не только при открытии их окон. Уже начатое чтение не прерывается и занимает место в очереди до ответа; устаревший результат не применяется, но сам сетевой запрос не отменяется.

Заметное облегчение обязательного boot-пакета также не завершено. Нужна дальнейшая работа с границами зависимостей `App` и роль-зависимых вычислений с повторным измерением полного пути до полезного экрана; текущие 484,91 KiB gzip нельзя выдавать за существенное сокращение первоначального скачивания.

Локальные проверки и браузерные фикстуры не заменяют p50/p95 на настоящем Telegram и медленной сети. Windows WebKit не подтвердил воспроизведение даже контрольного MP4 без приложения; это не результат Safari/iOS PASS.
