## P1 — исправить первым этапом

### T01. «Отмена» в редакторе клиента не соответствует фактическому сохранению

**Подтверждено цепочкой кода.** `TrainerClientsWorkspaceRoute.jsx:218` передаёт обработчик изменения упражнения. `trainerWorkspaceHandlers.js:30` вызывает `updateTrainerNextExercise`; `trainerPlanEditorHandlers.js:89` сразу меняет plan и запускает `saveWorkoutsToFirebase(nextPlan, { silent: true })`. Быстрые поля в `TrainerWorkspace.jsx:6915` вызывают это при вводе. При закрытии `closeEditor`, строка 2740, только закрывает окно — отката нет. При этом нижняя панель предлагает «Отмена»/«Сохранить», а `TrainerClientExerciseSheet.jsx` обещает применение изменений после сохранения программы.

**Последствие:** тренер может считать правки отменёнными, хотя запись уже запущена. Это не утверждение о проверенной записи в production: подтверждён путь выполнения кода.

**Исправить:** для модального редактора клиента использовать локальный черновик; отправлять его по «Сохранить». Закрытие без правок — сразу; с правками — понятное подтверждение. Отмена действительно отбрасывает черновик. Сохранить отдельный сценарий явного быстрого применения корректировки нагрузки.

**Приёмка:** ввод и «Отмена» не вызывают облачных записей; повторное открытие показывает исходные данные. Сохранение выполняет одну согласованную операцию; выполненная история неизменна.

### T02. После ошибки сохранения окно может закрыться как при успехе

**Воспроизведён контракт ошибки с синтетическими зависимостями.** `workoutPlanFirebaseSaveHandlers.js` в `catch` показывает ошибку, но не возвращает `false` и не пробрасывает исключение. `saveEditorChanges` в `TrainerWorkspace.jsx:2856` считает неудачей только `result === false` либо исключение. `undefined` проходит дальше к закрытию окна. Предупреждение об ошибке при этом действительно вызывается — проблема не в полном отсутствии уведомления, а в неверном завершении редактора.

**Исправить:** единый результат `{ ok, error }` или исключение; при неудаче оставить окно и черновик открытыми, дать повторить сохранение. Не закрывать связанный сигнал проверки тренировки до подтверждённого сохранения.

**Приёмка:** отказ чтения, отказ записи и offline не закрывают редактор; повторная попытка сохраняет тот же черновик.

### T03. Несколько быстрых изменений могут запустить конкурирующие сохранения всего плана

**Риск по коду, перестановка реальных сетевых ответов не воспроизводилась.** `persistPlan` запускает Promise без ожидания. `workoutPlanFirebaseSaveHandlers.js:51` перед каждым сохранением читает коллекцию workouts и профиль, затем формирует batch для плана. В этой цепочке нет очереди сохранения либо проверки ревизии. Быстрый ввод может отправить промежуточные значения и несколько полных снимков; позднее завершение старого запроса потенциально перезапишет более новый.

**Исправить:** после T01 сериализовать записи одной программы и проверять её ревизию при конкурентном редактировании. Не использовать один лишь debounce как защиту от разных вкладок.

**Приёмка:** искусственно задержанный старый запрос не возвращает устаревшие значения; конфликт двух вкладок явно обработан. Замерить количество записей за одно сохранение.

## P2 — следующий этап стабилизации

### T04. Сбой загрузки сводки превращается в «готовые» пустые данные

**Подтверждено кодом.** `trainerClientSummaryLoader.js:95` собирает `readFailures`, но использует их только для console.warn. `getTrainerSettledCollectionItems` (`trainerClientSummary.js:278`) возвращает пустой массив при ошибке. Далее рассчитываются показатели и выставляется `trainerSummaryReady: true`. Общий catch также возвращает пустую «готовую» сводку. Для процента выполнения есть отдельная проверка статуса history, но она не защищает остальные показатели.

**Исправить:** хранить статусы по источникам: загружается / актуально / ошибка / устарело; сохранять последние успешные значения. Не заменять сбой нулём и не вычислять сигналы неактивности на недоступных данных. Добавить повтор загрузки проблемного источника.

**Приёмка:** отказ history/measurements/tasks не показывает ложную неактивность; интерфейс обозначает, какие данные не обновились.

### T05. Глубокая сводка загружает весь объём историй каждого клиента

**Подтверждено кодом; количественный production-профиль не снимался.** `trainerClientSummaryLoader.js:87` читает полные history, measurements, workouts и trainerTasks, плюс документы nutrition/state и payments/current. Ограничение параллельности уже есть, однако объём чтения историй остаётся неограниченным. Повтор обновления повторяет эту работу для допустимых клиентов.

**Исправить:** для списка клиентов использовать агрегированную сводку, последние записи и ограниченный период; историю раскрывать с пагинацией. Не просто ограничить выборку и продолжать считать из неё пожизненные показатели — для них нужны отдельные агрегаты. Не перечитывать неизменившиеся данные без необходимости.

**Приёмка:** сравнить число чтений, время первого полезного экрана и полного обновления на 5/50/200 синтетических клиентах с годовой историей. Зафиксировать бюджет производительности после замеров.

### T06. Завершение общей синхронизации зависит от самого медленного запроса

**Риск по коду.** `loadClientSummary` ждёт `Promise.allSettled`, а общий loading снимается после `Promise.all(workers)`. requestId защищает от применения устаревшего результата, но сам по себе не завершает зависший запрос. Собственного ограниченного ожидания и состояния «частично обновлено» у этого загрузчика нет.

**Исправить:** добавить ограничение ожидания на уровне приложения, состояние частичного результата, повтор проблемных клиентов и время последнего успешного обновления. Поздние результаты должны применяться только к актуальному запросу. Кнопка продолжения в фоне полезна, но не заменяет эти состояния.

**Приёмка:** один зависший источник не удерживает всю сводку в неопределённом состоянии; остальные клиенты доступны и имеют достоверные статусы.

### T07. Сводка может одновременно сообщать о выполнении и отсутствии тренировок

**Воспроизведено в актуальном harness.** На карточке клиента: «1 из 3» и ниже «Пока нет завершённых тренировок». [Скриншот](../artifacts/trainer-audit-1366-0.png). В `TrainerWorkspace.jsx:4848` значение берётся из timeline назначения, а подпись — из `snapshot.lastWorkoutAt`; отсутствие даты трактуется как отсутствие завершений.

**Исправить:** согласовать источники числа и подписи. При известном завершении и неизвестной дате писать «Дата последней тренировки недоступна», а при загрузке обозначать загрузку.

**Приёмка:** отсутствующий/запаздывающий snapshot не противоречит известной истории и статусам дней.

### T08. Быстрые поля незаметно выравнивают все подходы и могут убрать их параметры

**Подтверждено кодом.** В `TrainerWorkspace.jsx:6915–6917` повторы и вес применяются через `sets.map` ко всем подходам. Уменьшение числа подходов обрезает массив; обратное увеличение копирует последний оставшийся подход, а не восстанавливает удалённые. Для упражнения с разными весами/повторами это содержательное изменение, которое из компактного поля не очевидно.

**Исправить:** явно назвать область действия «Все подходы», для неодинаковых значений показывать «Разные» и предлагать редактирование по подходам. Удаление подходов сделать обратимым в черновике. Для повторов добавить подходящую цифровую клавиатуру там, где формат допускает только числа.

**Приёмка:** схема 12/10/8 и 20/25/30 кг не унифицируется без понятного действия; сокращение/отмена возвращает исходный набор.

### T09. Регрессионные UI-тесты отстали от реального интерфейса

**Подтверждено запусками.** Все 8 `client-four` падают на ожидании четырёх строк старой `.trainerClientMeasurementTable`, после прохождения предыдущих проверок вкладок. Responsive-тест останавливается на отсутствии совпавших старых селекторов навигации при 768 px; тест окон — на отсутствии старого атрибута поверхности. В workspace есть strict-mode ошибка слишком общего `getByRole('button')`, ожидания прежней кнопки прогресса, прежнего расположения истории программ и старого inline-редактора. Другие падения требуют отдельного разбора сценария, включая выбранное окно «Поддержка» вместо ожидаемого расписания.

**Важно:** это не доказательство 18 неисправных функций продукта. Часть причин явно в тестах; не все сценарии дошли до проверки функционального результата. Тест, который остановился на селекторе, не подтверждает исправность последующих шагов.

**Исправить:** обновить сценарии на актуальные пользовательские действия и доступные имена, затем восстановить зелёную базу. Добавить реальные проверки черновика/сохранения/ошибки/повторного открытия с подменяемым persistence, а не только проверять HTML и no-op callbacks.

**Приёмка:** согласованный набор проходит; намеренно внесённая ошибка сохранения или доступа действительно обнаруживается.

## P3 — удобство и визуальная согласованность

### T10. Часть вторичных подписей слишком мелкая

**Подтверждено CSS.** В `TrainerClientWorkoutPlan.module.css:1672` подписи быстрых полей имеют 10 px. Компактность достигнута за счёт текста, которым тренер различает параметры. На телефоне это требует лишнего внимания, даже если само поле не перекрывается.

**Исправить:** поднять важные подписи до согласованного читаемого размера, уменьшать повторы и декоративные отступы; сохранить поля не меньше 44 px по высоте и проверять масштаб текста. Не решать переполнение дальнейшим уменьшением шрифта.

**Приёмка:** названия параметров читаются при 320 px и увеличенном тексте; нет обрезания и новых пересечений.

### T11. Два редактора выглядят ближе, но имеют разные договорённости об изменениях

**Подтверждено сравнением компонентов.** Библиотека использует `TrainerProgramConstructor`/`TrainerProgramManagerView` с отслеживанием изменений, клиент — `TrainerWorkoutEditor` внутри `TrainerWorkspace` с другой цепочкой сохранения. Кроме T01, это усложняет одинаковое поведение закрытия, изменения подходов, выбора видео и восстановления после ошибки.

**Исправить:** зафиксировать общий контракт редактора и постепенно переиспользовать небольшие части: строку упражнения, поля подходов, окно видео, обработку закрытия. Сохранить различия ролей: шаблон и индивидуальная программа — разные сущности; выполненная история клиента защищена.

**Приёмка:** одни и те же действия имеют одинаковый результат; различия объяснены пользователю и покрыты проверками. Массовое переписывание `App.jsx` не нужно.

### T12. Каскад стилей делает следующие визуальные изменения хрупкими

Последний дефект с кнопкой исправлен и текущий probe проходит; наличие каскада не означает, что перекрытие осталось.

**Исправить:** локально свести правила конкретного ряда к одной сетке и одному месту определения размеров. Общие отступы/радиусы/цвета брать из действующих токенов. Удалять старые перекрытые правила только после проверки всех затронутых вариантов.

**Приёмка:** 320/393/760/1081/1280/1600 px, длинные названия, отсутствие видео, история упражнения, завершённый день и открытые настройки остаются корректными.
