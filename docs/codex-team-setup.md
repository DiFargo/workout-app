# Codex: второй Windows-компьютер

Цель — одинаковые правила работы с GymDuck, не копирование аккаунта владельца. Этот документ не заменяет [AGENTS.md](../AGENTS.md) и не выдаёт доступ к Production.

## Что переносится

| Часть | Как получить |
| --- | --- |
| Правила | `AGENTS.md` и `.codex-instructions` из согласованной версии репозитория |
| Контекст | `index.md`, `project_map.md`, `docs/`, а не вся история чатов |
| Навыки | `.agents/skills/`; `ui-ux-pro-max` уже в Git, остальные — из team kit |
| Модель и рассуждение | Выбрать одинаковые доступные значения в личных настройках |
| Плагины, MCP, инструменты | Настроить отдельно на втором компьютере, только необходимые |
| Аккаунты и секреты | Не передаются; собственный вход в Codex/Git, отдельные тестовые доступы |

`AGENTS.md` — основной автоматически обнаруживаемый файл правил. `.codex-instructions` явно включён в договор через `AGENTS.md`; произвольное имя файла само по себе не гарантирует автоматическое чтение.

Совпадение правил не гарантирует одинаковые ответы: история чата, память, инструменты и политики компьютера могут различаться. Надёжность проверяется тестами и review.

## Подготовка владельцем

1. Выбрать актуальную стабильную ветку/commit. Не считать локальную `main` автоматически самой новой опубликованной версией.
2. Дать отдельному Git-аккаунту брата доступ к приватному репозиторию. Не передавать свои токены и сессии.
3. Включить этот документ и правила в согласованную ветку: незакоммиченные файлы с первого компьютера в clone не попадут.
4. Собрать дополнительный пакет навыков:

   ```powershell
   node .\scripts\export-codex-team-kit.mjs
   ```

Скрипт читает только 13 явно перечисленных каталогов навыков и этот документ. Новый ZIP появляется в `output/codex-team/`. Исходники приложения, личный `config.toml`, `auth.json`, `.env`, история чатов и Firebase/Git-сессии не входят в источники экспорта. Экспорт не меняет Windows Execution Policy и не требует запуска `.ps1`.

Перед передачей проверить состав архива и SHA-256 по `manifest.json`. Экспорт отклоняет ссылки, известные имена файлов учётных данных и материал private key, но это не универсальный поиск секретов под произвольными именами. Проверка содержимого остаётся обязательной; не добавлять в каталоги навыков личные данные и ключи.

Пакет — снимок навыков, а не приложения. В дальнейшем согласованно включить нужные навыки в `.agents/skills/` стабильной ветки и обновлять через review.

## Подготовка второго компьютера

1. Установить Codex, войти под собственным аккаунтом. Использовать сопоставимую версию приложения.
2. Установить Git, Node.js 22 и Python 3. Java 21 нужна для Firebase Rules. Установку/права администратора подтверждает владелец компьютера.
3. Клонировать согласованную ветку. Открыть в Codex корневую папку с `AGENTS.md`.
4. Проверить репозиторий и подтвердить доверие проекту. Не включать Full Access ради совпадения настроек; сохранять ограниченную запись в рабочую папку и подтверждение чувствительных действий. Управляемые политики имеют приоритет.
5. Распаковать team kit сначала в отдельную пустую папку. Проверить `manifest.json`, затем добавить недостающие каталоги из `.agents/skills/` в такую же папку проекта. Отличающиеся существующие навыки не заменять без согласования. Снова открыть проект/начать новый чат и проверить обнаружение навыков.
6. Сверить доступные модель и уровень рассуждения. Не копировать целиком чужой `%USERPROFILE%\.codex\config.toml`. Общий `.codex/config.toml` можно добавить позднее согласованной правкой; сейчас проект его не задаёт.

Нельзя передавать целиком `%USERPROFILE%\.codex`, `.config`, Firebase/npm-кэши, Git credentials, production `.env*` или service-account JSON. Правила — не учётные данные.

## Первый запуск без Production

Проверить `node --version`, `npm.cmd --version`, `git --version`, `python --version`, `java -version`.

Для начала работы с UI:

```powershell
npm.cmd ci
npx.cmd playwright install chromium webkit
```

Для проверок Functions/Rules дополнительно выполнить `npm.cmd ci` в `functions` и `functions-telegram-auth` по [index.md](../index.md).

Локальный просмотр админки с фиктивным окружением из `playwright.config.js`:

```powershell
$env:VITE_FIREBASE_ENVIRONMENT='e2e'
$env:VITE_FIREBASE_API_KEY='AIzaSyA12345678901234567890123456789012'
$env:VITE_FIREBASE_AUTH_DOMAIN='workout-app-e2e.firebaseapp.com'
$env:VITE_FIREBASE_PROJECT_ID='workout-app-e2e'
$env:VITE_FIREBASE_STORAGE_BUCKET='workout-app-e2e.appspot.com'
$env:VITE_FIREBASE_MESSAGING_SENDER_ID='000000000000'
$env:VITE_FIREBASE_APP_ID='1:000000000000:web:e2e'
npm.cmd run dev -- --host 127.0.0.1 --port 4174 --strictPort
```

Открыть [локальную админскую фикстуру](http://127.0.0.1:4174/?adminHarness=1). Это DEV-harness с демонстрационными данными, не реальная админская сессия. Фиктивные Firebase-значения не дают доступ к серверным операциям. Для настоящих интеграционных сценариев нужно отдельно согласованное development/staging-окружение: [environments.md](environments.md).

Проверка существующего интерфейса:

```powershell
npm.cmd run test:e2e -- tests/e2e/admin-visual.spec.js
```

Playwright сам задаёт e2e-окружение. Не выставлять `PW_REUSE_SERVER=1` без проверки изоляции. При занятом порте остановить свой DEV-процесс, не подключаться к неизвестному серверу.

## Первое сообщение в Codex

```text
Работаем над GymDuck в этой папке. Полностью прочитай AGENTS.md и .codex-instructions, затем index.md и нужный раздел project_map.md. Проверь доступные навыки проекта и используй подходящие.

Начальная область — интерфейс админки. Работаем от согласованной актуальной стабильной базы в отдельной ветке codex/admin-<задача>. Не откатывай чужие изменения, не переписывай общую архитектуру.

В этой задаче не меняй Firebase, Rules, роли, авторизацию, удаление данных и Telegram без отдельного согласования. Не читай реальные клиентские данные и не публикуй в Production. Используй локальный adminHarness с e2e-конфигом.

Перед правкой обозначь короткие критерии готовности. После неё выполни проверки по AGENTS.md и просмотри diff. Отчитайся по-русски: что изменено, что проверено, что осталось непроверенным.

Сначала проверь среду и правила без изменения приложения. Покажи текущую ветку/commit, версии инструментов, найденные правила и навыки, возможность открыть локальную админскую фикстуру. Не выводи ключи и личные конфиги.
```

## Готовность рабочего места

- [ ] Собственные аккаунты, правильный корень репозитория и согласованная стабильная база.
- [ ] Отдельная рабочая ветка без неожиданных исходных изменений.
- [ ] Codex прочитал правила и карту, обнаружил нужные навыки.
- [ ] Модель/уровень рассуждения сверены, ограничения аккаунта и компьютера учтены.
- [ ] Локальная фикстура открывается, профильная UI-проверка работает.
- [ ] Нет общих личных сессий, Production-ключей или реальных клиентских данных.
- [ ] Изменения передаются отдельной веткой/PR; публикация — после согласования владельцем.
