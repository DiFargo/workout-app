# Динамичная кнопка тренировки — 3.0.857

Утверждён вариант «Свободный экран». Изменение касается активного упражнения: вместо двух нижних переходов — одна основная кнопка. Публикация разрешена пользователем 22 октября 2026 года.

## Единый список приёмки

- [x] «Подход выполнен» отмечает только текущий доступный подход и оставляет его на экране.
- [x] Следующее отдельное нажатие переводит к следующему подходу; после всех подходов — к следующему упражнению, после последнего — в штатное завершение.
- [x] Отдых остаётся компактным, доступно ручное раскрытие; пропуск остатка отдыха при переходе явно подписан.
- [x] Ошибочную отметку можно отменить; прошлые подходы доступны через номер, будущие нельзя выполнить раньше очереди.
- [x] Двойное нажатие не выполняет два разных шага. Таймер упражнения не снимает уже поставленную отметку поздним событием.
- [x] Порядок суперсетов/трисетов и отдых после круга сохранены.
- [x] Видео не перемонтируется при смене подхода, сохраняет квадрат и кадрирование. Видео, подход, отдых и основная кнопка помещаются на обычном мобильном экране.
- [x] Редактирование, черновик, история, Firebase на staging/Production, разминка, feedback и результат проверены в описанном объёме.
- [x] Профильные проверки, сборки и staging/Production smoke выполнены; результат и ограничения записаны ниже.
- [x] Пользователь подтвердил поведение в настоящем Telegram после повторного открытия.

Пользователь подтвердил: «Да, всё работает и помещается». На его устройстве после повторного открытия Telegram одна нижняя кнопка корректно меняет действия, а видео, подход и отдых помещаются на экран. Это нативная приёмка на проверенном пользователем устройстве, не утверждение о всех устройствах. Runtime не менялся, повторная публикация не потребовалась.

## Устройство изменения

Чистая модель `workoutPrimaryAction.js` выбирает действие по фактическим подходам и разрешённым индексам текущего execution step. Состояние выбора привязано к тренировке и шагу. Footer вызывает существующий метод подтверждения компонента подходов: активный/приостановленный timed-таймер корректно отменяется до записи отметки. Ни вес, ни повторы, ни история этим выбором не изменяются.

Вместо стрелок остался раскрывающийся номер подхода; там можно просматривать выполненные подходы и возвращаться к текущему. Предыдущий экран упражнения доступен кнопкой в шапке. Штатные обработчики навигации, feedback и сохранения не заменены. Случайный повторный тап в пределах 400 мс не выполняет второй шаг.

Автоматическое раскрытие отдыха убрано; ручное сохранено. При пропуске отдыха исправлен найденный эффект cleanup: он больше не восстанавливает остаток старого таймера поверх явного сброса в ноль. Обычная пауза продолжает сохранять остаток времени.

Адаптированный существующий браузерный набор: 19 desktop-сценариев прошли, 1 ожидаемый skip; 4 мобильных сценария прошли. В этот набор входят две встроенные проверки WebKit, 7 профилей телефонов, landscape, увеличенный текст, редактор подхода, разминка и сохранённый результат. Полный `verify:full` с Rules/Functions/dependency audit не запускался: backend, Rules и зависимости не меняются. Выбранные проверки соответствуют риску по `AGENTS.md`; это не полный повторный аудит приложения.

## Наблюдение после публикации

Read-only наблюдение выполнено существующим `scripts/inspect-production-release-health.mjs` через Node 22 и текущую авторизованную сессию Firebase CLI. Фиксированные окна отсчитываются от подтверждённой публикации `2026-10-22T13:20:53.093Z`:

- `artifacts/remediation-3.0.857/production-health-interim-5m.json`: окно 13:20:53.093–13:25:53.093 UTC; запрос завершён в 13:26:17.811 UTC, код завершения 0.
- `artifacts/remediation-3.0.857/production-health-final-30m.json`: окно 13:20:53.093–13:50:53.093 UTC; запрос завершён в 13:51:19.178 UTC (16:51:19.178 по Минску), код завершения 0.

В обоих отчётах все шесть запросов вернули HTTP 200, `pages:1`, `truncated:false`, `status:no_data`. Это означает, что по фильтрам ERROR+, структурированных квот/429 и четырёх метрик квот/429 записи или временные ряды не возвращены. Это не подтверждённый ноль ошибок, не измерение запаса квот и не доказательство исправности всех клиентов.

Во всех четырёх метриках обоих отчётов стоит `freshness.windowMayStillBeIncomplete:true`: запросы выполнены вскоре после конца соответствующих окон. У `quotaExceeded` нет документированной верхней границы задержки видимости; у остальных сигналов границы составляют 1860, 300 и 180 секунд. Поздние данные ещё могут поступить. Повтор того же итогового окна после созревания всех метрик в этот 30-минутный этап не входил.

Первый пятиминутный запрос в sandbox завершился неуспешно: все шесть проверок получили `transport_timeout_or_invalid_response` без HTTP-ответа (`pages:0`, `truncated:true`). Его санитаризированный отчёт сохранён отдельно: `artifacts/remediation-3.0.857/production-health-interim-5m-sandbox-transport.json`. После разрешённой read-only сетевой эскалации повтор прошёл; итоговый запрос использовал тот же разрешённый путь. Первичная транспортная недоступность не скрыта и не трактуется как отсутствие ошибок приложения.

Наблюдение сохраняет только агрегаты: сырые журналы, секреты, токены, идентификаторы и содержимое пользовательских записей не выводились. В ходе этого наблюдения IAM, API, ресурсы, аккаунты и данные не изменялись; повторной публикации и mutating Production smoke тогда не было. Позже, после отдельного согласия пользователя, authenticated-проверка выполнена отдельно, как описано выше. Запросы наблюдения относятся ко всему проекту, не выделяют конкретную клиентскую сборку и не подтверждают обновление уже открытых мини-приложений. Наблюдение и браузерный smoke не заменяют отдельную нативную приёмку пользователем.
