## P1 — безопасность и сохранность данных

### R01. Смена email допускается сервером без повторного подтверждения личности

**Воспроизведено исполнением endpoint с synthetic auth.** [functions/index.js:3786](C:/Users/workk/workout-app/functions/index.js:3786) требует активную сессию, но не недавнюю аутентификацию; [строка 3835](C:/Users/workk/workout-app/functions/index.js:3835) меняет email через Admin SDK. Проверка пароля/Google reauth есть лишь в [клиентском обработчике:270](C:/Users/workk/workout-app/src/features/client/profile/profileAccountHandlers.js:270), который можно обойти прямым запросом.

С `auth_time: 1` реальный handler вернул 200 и вызвал операцию смены email в mock. Условие — уже полученный действующий ID token либо оставленная активная сессия. Это **не** неавторизованный захват с нуля. Смена адреса с последующим password reset может превратить временный доступ в постоянный, в том числе к аккаунту тренера/администратора.

**Исправить:** server-side recent-auth gate, проверку отзыва сессии для чувствительных действий и подтверждение новой почты до замены. UI-проверка не является границей безопасности. Firebase отдельно описывает необходимость недавней аутентификации для чувствительных операций: [Manage users](https://firebase.google.com/docs/auth/web/manage-users#re-authenticate_a_user).

**Приёмка:** старый `auth_time` → отказ без записей; свежая reauth → допустимое продолжение; неподтверждённый адрес не заменяет действующий.

### R02. Через изменяемые поля профиля можно удалить/перепривязать чужой login alias

**Воспроизведено Rules Emulator + исполнением настоящих handlers.** [firestore.rules:127](C:/Users/workk/workout-app/firestore.rules:127) не защищает `loginLower` и `accountProfile.login`. Сервер доверяет этим полям как текущему alias: [functions/index.js:3984](C:/Users/workk/workout-app/functions/index.js:3984), затем удаляет старую alias-запись без проверки её владельца на строках 4018–4019. Email endpoint может её перезаписать: [строка 3852](C:/Users/workk/workout-app/functions/index.js:3852).

Синтетический клиент подставил в собственный профиль чужой известный логин; смена своего логина породила удаление чужого alias, смена email — запись alias с UID атакующего. Последствие — отказ входа по логину/подмена его маршрутизации. **Захват Firebase Auth аккаунта жертвы этим сценарием не доказан; вход по её email может сохраняться.**

**Исправить:** server-owned login identity, проверка UID старого и нового alias, транзакционная проверка коллизий. Запретить клиентскую запись служебных login-полей.

**Приёмка:** подставленный чужой alias и конкурентное занятие одного логина не изменяют чужие документы.

### R03. Общий wildcard Firestore разрешает клиенту подделывать данные тренера

**Подтверждено эмулятором, проблема из предыдущего аудита сохраняется.** [firestore.rules:963](C:/Users/workk/workout-app/firestore.rules:963) разрешает владельцу `read/write` во всех подколлекциях пользователя. Правило пересекается с ограничениями `trainerTasks`, `trainerEvents`, `payments` выше. Совпадающие разрешения объединяются через OR: [Rules structure](https://firebase.google.com/docs/firestore/security/rules-structure).

Обычный активный клиент смог создать `payments/current`, изменить текст/автора задания, удалить задание и событие тренера. В [trainerClientSummaryLoader.js:91](C:/Users/workk/workout-app/src/features/trainer/trainerClientSummaryLoader.js:91) платёж читается для сводки, а [clientInsights.js:120](C:/Users/workk/workout-app/src/domain/clientInsights.js:120) позволяет подложным `controlUntil` скрыть legacy overdue-сигнал. **Обход оплаченного доступа не доказан: subscription защищён отдельно.**

**Исправить:** явный список разрешённых клиентских коллекций/операций вместо общего owner-write. Не ломать законное завершение задания клиентом.

**Приёмка:** отрицательные create/update/delete-тесты для всех trainer-managed коллекций, вложенных путей и неизвестных коллекций; изменения допускаются только в разрешённых полях.

### R05. При переполненном localStorage результат теряется под сообщением «Сохранено локально»

**Воспроизведено реальным save-handler с quota mock.** [storageSafety.js:47](C:/Users/workk/workout-app/src/utils/storageSafety.js:47) сокращает любой массив вплоть до `[]`, после чего может вернуть `true`. Эту функцию использует обязательная очередь результатов: [offlineSyncStorage.js:83](C:/Users/workk/workout-app/src/utils/offlineSyncStorage.js:83). [workoutFirebaseSaveHandlers.js:207](C:/Users/workk/workout-app/src/features/client/workouts/workoutFirebaseSaveHandlers.js:207) после этого показывает локальный успех и удаляет draft.

Получено: `saved=true`, `sync=local`, persisted queue `[]`, draft отсутствует. Дополнительно шаблон `/backup|failed_sync|pending/` считает очереди с несинхронизированными данными удаляемыми «backup».

**Исправить:** lossless-запись обязательных очередей отдельно от ограниченных резервных снимков; проверять результат записи, сохранять черновик при неудаче. Не удалять pending-данные при очистке места.

**Приёмка:** quota при одном/нескольких результатах не теряет ни запись, ни draft и не выдаёт ложный успех.

### R06. Replay стирает новые результаты, добавленные во время синхронизации

**Воспроизведено с отложенным запросом.** [offlineReplayHandlers.js:22](C:/Users/workk/workout-app/src/features/client/offline/offlineReplayHandlers.js:22) берёт snapshot очереди, а [строка 47](C:/Users/workk/workout-app/src/features/client/offline/offlineReplayHandlers.js:47) заменяет актуальную очередь старым `remaining`.

Пока отправлялся A, новая неудачная запись B попала в очередь. После replay: cloud содержит только A, очередь пустая. Backup B может остаться, но автоматический путь восстановления из него не найден. Это отдельный дефект, не зависящий от quota.

**Исправить:** перечитывать актуальную очередь и удалять только успешно отправленные ID; для нескольких вкладок — согласованная транзакция/операционная очередь. Проверить аналогичные snapshot→replace replay в питании и замерах, не ограничиваться историей.

**Приёмка:** B сохраняется при ожидающем A; частичные ошибки и повторный replay не дают потерь/дублей.
